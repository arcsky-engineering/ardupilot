# Xplorer parameter documentation

Generates the Xplorer parameter disposition document — every parameter the
aircraft exposes, with its default, read-only state, visibility, enforced range
and description — as **CSV, XLSX and a searchable HTML page**.

```bash
python Tools/xplorer/gen_param_docs.py                    # all three outputs
python Tools/xplorer/gen_param_docs.py --format html      # just the web page
python Tools/xplorer/gen_param_docs.py --refresh-metadata # re-read @Param docs
python Tools/xplorer/gen_param_docs.py --check            # CI: fail on drift
```

Outputs land in `doc/params/`. **They are build artifacts — never hand-edit
them.** Edit an input and regenerate.

## Why this exists

The disposition sheet used to be maintained by hand in Google Sheets. When it was
last audited against firmware, the generated rows had **zero** errors and the
nine hand-added rows had **three**. Nine parameters (`BATT*_LOW_SOC`,
`BATT*_CRT_SOC`, `BATT*_ARM_SOC`) had also been missing from the sheet for two
months because nothing connected the sheet to the source. This tool closes both
gaps: the document is derived from source, and `--check` fails when it drifts.

## Where each column comes from

| Column | Truth source |
|---|---|
| `default` | `hwdef/<board>/defaults.parm`, falling back to a Lua applet's `PARAM_TABLE` |
| `read_only` | the `@READONLY` marker in `defaults.parm` |
| `user_visible` | `AP_PARAM_FLAG_HIDDEN` scraped from the `var_info` tables |
| `clamp_min` / `clamp_max` | `libraries/GCS_MAVLink/GCS_Param_Clamps.h` (enforced) |
| `doc_range_min` / `max` | the `@Range` annotation (documented, *not* enforced) |
| `display_name`, `description`, `units`, `values`, `bitmask`, `user_level`, `reboot_required` | `apm.pdef.json`, generated by `Tools/autotest/param_metadata` |
| `notes` | `param_notes.csv` — **the only hand-authored input** |

`clamp_*` and `doc_range_*` are deliberately separate: the clamp table is what
actually rejects a `PARAM_SET`, the `@Range` is only advice and the two disagree
in places (e.g. `LOIT_SPEED` documents 20–3500 but is clamped 50–2000).

## The four editable inputs

- **`param_notes.csv`** — human notes, keyed by name. Everything else in the
  output is generated, so this is where operational knowledge lives. Safe to
  edit freely; unknown names are ignored.
- **`param_manifest.txt`** — the authoritative row set. Needed because a
  parameter only appears in a GCS download when its feature is enabled
  (`RNGFND3_TYPE=0` collapses the whole `RNGFND3_` subgroup), and that cannot be
  determined from source. Comes from a real param download. Its header records a
  `baseline-commit`.
- **`param_meta_overrides.json`** — metadata for params the upstream parser
  cannot read. Currently one entry: `FLTMODE_GCSBLOCK`, whose repeated per-line
  `@Bitmask{Copter}:` entries defeat `param_parse.py`'s block regex. The tool
  warns when an override becomes redundant.
- **`param_check_waivers.csv`** — sanity-check findings that are accepted rather
  than fixed, each with a reason. Currently one: `PSC_VELZ_IMAX`, an upstream
  range-annotation bug.

## What `--check` catches

Exit code 1 on any of:

1. **A parameter added to the firmware but missing from the manifest.** Diffs
   `baseline-commit..HEAD` for added `AP_GROUPINFO`/`GSCALAR` definitions. This
   is the check that would have caught the SOC params.
2. **A parameter in `defaults.parm` that is not in the manifest.**
3. **Outputs out of date** — regenerates to a temp dir and compares (the
   timestamp is stripped, so time alone never trips it; XLSX is skipped because
   its bytes are not reproducible, CSV covers the same data).
4. **A seeded default outside the parameter's own documented range.** Found
   `PTRN_CHN2 = 16` against a script range of 5–12, silently clamped to 12.
5. **A seeded default outside its own clamp window**, which the boot scrub would
   rewrite.
6. **`AP_PARAM_FLAG_HIDDEN` in a source file the tool does not know about** —
   hard failure, because visibility would silently go stale otherwise. Add the
   file to `HIDDEN_SOURCES` (with the prefix its `var_info` sits under) or to
   `HIDDEN_IGNORE`.

Findings matching the common upstream "0 means disabled, outside the useful
range" idiom are reported as notices, not problems.

Suggested pre-commit / CI hook:

```yaml
- name: Xplorer parameter docs up to date
  run: python Tools/xplorer/gen_param_docs.py --check
```

## Publishing the HTML

`doc/params/xplorer-params.html` is fully self-contained — no external CSS, JS or
fonts — so it works from a file share, an S3 bucket, GitHub Pages or an intranet
path with no build step. It has client-side search across name, description,
notes and enum values, group and flag filters, and light/dark support. Every row
is anchored (`…xplorer-params.html#BATT2_LOW_SOC`) so support can link a
colleague straight to one parameter.

## Adding a new parameter — the whole checklist

1. Add the `AP_GROUPINFO` with a full `@Param` doc block (`@DisplayName`,
   `@Description`, `@Units`, `@Range`, `@Values`/`@Bitmask`, `@User`).
2. Seed it in **both** `CubeOrangePlus-ODID/defaults.parm` and
   `CubeOrangePlus/defaults.parm` (kept byte-identical), adding `@READONLY` if it
   should be locked.
3. Add the name to `param_manifest.txt`, and a row to `param_notes.csv` if
   there is anything non-obvious about it.
4. Add a clamp in `GCS_Param_Clamps.h` if it needs a hard bound. Skip this when
   `0` means "disabled" — a single min/max window cannot express "0 or 15..40",
   and the boot scrub would rewrite a deliberately-disabled value.
5. Run `python Tools/xplorer/gen_param_docs.py` and move `baseline-commit` in
   the manifest to HEAD.

Lua applet params work the same way: document them with `// @Param:` blocks
inside `--[[ ]]`, exactly as `libraries/AP_Scripting/applets/BattEstimate.lua`
does, and register the applet in `LUA_APPLETS`.
